Balaji CRM

An internal CRM for a small real-estate brokerage, covering the problem, the solution, the stack, the architecture, and the deployment.

01

Problem statement

A small real-estate brokerage — an owner plus a staff of closing agents and a cold-calling team — currently runs entirely on WhatsApp, phone calls, and scattered notes. That produces three concrete, named problems.

Problem 1

No unified inventory

Property listings are scattered across hundreds of WhatsApp broker groups. Agents cannot quickly find matching inventory for a client's budget and location — they scroll chat history and rely on memory.

Problem 2

No owner visibility

The owner has no way to know which agent is showing which property to which client, or whether a lead is actually being followed up. Oversight depends on staff volunteering the information.

Problem 3

Data leakage risk

There is no access control or audit trail. An agent can walk away with the firm's entire client list — a real, stated risk when staff leave to join a competitor or freelance on the side.

The realistic threat is not an external hacker. It is an insider with legitimate login access trying to extract the client/lead list. Every access-control decision in this system is designed against that specific threat, not a generic one — see §7.

02

The solution

Balaji CRM answers each of the three problems with a structural mechanism, not a bolted-on feature — meaning the fix is enforced in the query layer or middleware, so it cannot be forgotten by some future screen.

→ Problem 1

Automated WhatsApp inventory feed

A gateway service reads the firm's monitored WhatsApp groups directly. An LLM extracts structured fields (location, building, BHK, price, rent vs. sale) from free-text posts, de-duplicates reposts of the same flat, and writes one unified, searchable, filterable inventory — with the original message retained for provenance.

→ Problem 2

Structural activity logging

Every call, site visit, and property-shown-to-client event is its own row, not a mutable field. The owner's live activity feed reads directly from that same table, so "what the owner sees" is always in sync with "what actually happened," with no separate reporting pipeline to drift out of date.

→ Problem 3

Role-scoped access + immutable audit log

Role-based access control is enforced at the query layer (an agent's query is scoped to their own leads at the SQL level, not filtered in the UI). Bulk export exists only for Owner/Manager, every export is itself logged, and the audit log is structural middleware — not something an endpoint has to remember to call.

What is actually built

Core CRM

  • Role-scoped contacts/leads, with masked phone numbers until a qualifying interaction is logged
  • Property inventory: manual entries + WhatsApp-sourced listings in one searchable, filterable view
  • Site-visit / showing tracking (“who showed what to whom, when”)
  • One-tap call logging with outcome + temperature + notes
  • Owner activity feed, escalation inbox, team performance view
  • Immutable, append-only audit log with an audit viewer for the Owner
  • Lead import (bulk CSV/XLSX) with dedup against existing contacts
  • Web-push notifications (follow-ups, escalations)

WhatsApp inventory pipeline

  • Node/Baileys gateway holds a real WhatsApp Web session and forwards group messages to the backend over a shared-secret webhook
  • Messages are journalled raw before parsing, so a prompt fix can be replayed over history without re-reading WhatsApp
  • Groq-hosted LLM extraction with a JSON schema, cheap pre-filtering of obvious non-listing chatter, and multi-model rate-limit rotation
  • Fuzzy dedup merges reposts of the same flat into one listing with multiple sightings, rather than duplicating rows
  • A pairing flow inside the app itself (QR code, group picker) — no terminal access needed once the gateway process is running

Why a PWA, not a native app

One codebase instead of two; faster iteration with no App Store review gate; service workers give good-enough offline viewing of recently-loaded leads/properties. If the team ever needs deep native capability (background location, offline writes), the FastAPI backend and data model don't need to change — only the frontend layer would be rebuilt.

Why Groq for extraction

A busy brokerage generates thousands of messages a day, and the task is structured copying out of messy text, not reasoning — it doesn't need a frontier model. The trade-off: Groq has no prompt caching, so the system prompt is repaid on every call, and free-tier rate limits are tight enough to require multi-model rotation (see §8).

Component notes

Frontend — Next.js PWA

Role-aware routing: Owner, Agent, and Cold Caller each land on a different home surface. The browser never calls FastAPI directly — every request goes through a Next.js API route (/api/crm/[...path]) that attaches the session JWT from an httpOnly cookie, so the API base URL is never exposed to client code.

Backend — FastAPI

RBAC middleware (app/rbac.py, app/scoping.py) resolves the caller's role on every request and scopes queries accordingly. Audit middleware (app/audit.py) wraps every read/write on sensitive resources. Neither is opt-in per endpoint.

Database — PostgreSQL

Soft delete everywhere (deleted_at), never hard delete — the audit trail must survive record deletion. Every interaction (call, visit, remark) is its own row in call_logs/activities, not a mutable field on the lead.

WhatsApp gateway — isolated by design

Kept as a separate Node service, deliberately outside the main FastAPI app: it is the one component built on an unofficial integration (WhatsApp Web, not the Business API), and isolating it limits the blast radius if the session drops or WhatsApp rate-limits it — it cannot take down the core CRM.

Fuzzy-matched against existing properties rows by building + BHK + price.

6

New listing inserted, or an existing one gains another sighting — queryable immediately by any staff with inventory-view permission.

1
Call placed

Cold caller works their queue, logs outcome via the remark form.

2
Call log written

POST /calls — its own row, not a field update.

3
Audit entry written

By middleware, automatically.

4
Follow-up or escalation

A qualifying outcome auto-creates a follow-up task; a flagged call lands in the owner's escalation inbox with a push notification.

5
Owner sees it live

The owner's activity feed reads the same table — no separate reporting pipeline to fall out of sync.

Threat model

Not an external hacker — an insider with legitimate login access trying to extract the client/lead list before leaving. Mitigations: mandatory pagination and masking (raises the cost of manual scraping), no export capability for Agent/Cold Caller at the API level (not just hidden in the UI), and prompt session invalidation on deactivation.

Audit logging

Structural, via FastAPI middleware wrapping every request that touches contacts, properties, call logs, or an export endpoint — no endpoint has to remember to log. Where the database allows it, UPDATE/DELETE on audit_log is revoked from the application's own DB role, so even the app's own credentials cannot rewrite history.

Cold Caller scope

Sees exactly one surface — their queue — and of the client only a name and mobile number. No lead list, no lead detail, no inventory. Enforced as capabilities the role simply does not hold, so the missing nav items are a consequence of the API refusing the request, not the only control.

Sessions

Sliding expiry with an absolute cap: a token renews itself while in use (SESSION_IDLE_DAYS, default 30) but can never live past a fixed ceiling from first login (SESSION_ABSOLUTE_DAYS, default 90) — so no amount of use makes a session permanent.

Why the gateway is deployed separately

It drives a real WhatsApp account over an unofficial integration and keeps the linked-device session on disk. Running it on hardware the firm controls keeps that blast radius visible; running it on Render works too, but only with a paid persistent disk — without one, every deploy wipes the session and forces a fresh QR re-link, which is the single most account-flagging thing this process can do.

Extraction throughput

Groq's free tier caps at 8,000 tokens/minute and 1,000 requests/day per model. EXTRACTION_MODEL takes a comma-separated list tried in order, so multiple model names become multiple independent rate-limit buckets on the same key — a model on cooldown is skipped rather than failing the batch.

Operating costs & known limits

Vercel (Hobby)Free

Render Web Service (API)Free, sleeps after 15 min idle
Render Background WorkerNot free — ~$7/mo, needed only for the WhatsApp feed
Groq APIUsage-based; free tier is usable but rate-limited, only relevant if the WhatsApp feed is in use

A working CRM without the WhatsApp feed costs nothing beyond the database, after the first 90 days. The feed is what introduces both the recurring worker cost and the operational responsibility of keeping a WhatsApp session alive.

Deliberate non-goals

  • No native mobile app — PWA only, by design (see §3)
  • No payment/commission processing
  • No public-facing, buyer-facing listing site — internal tool only
  • No legal/document e-signing workflows

What the security model does not attempt

It cannot stop an agent from memorizing or manually writing down a small number of contacts they're actively working — no software control fully prevents this. The realistic goal is raising the cost and visibility of large-scale extraction, not making leakage physically impossible. Device-level MDM and screenshot prevention are explicitly out of scope for a small-team internal tool.
